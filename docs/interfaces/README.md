# Numark Mixtrack Platinum FX — MIDI interface reference

This is a byte-level reference for the MIDI interface of the **Numark Mixtrack Platinum FX**, as implemented by this repository's Mixxx controller mapping. It documents, for every physical element of the controller, the exact MIDI bytes involved: what the controller **sends** when you touch it (input) and what Mixxx must **send back** to drive its LEDs and screen (output).

It has been generated by Claude Code from the two reference/original source files in [`original/`](../../original/):

- [`Numark Mixtrack Platinum FX.original.midi.xml`](<../../original/Numark Mixtrack Platinum FX.original.midi.xml>) — the declarative Mixxx `<control>` / `<output>` mappings (status byte, midino, target Mixxx `group`/`key`, options).
- [`Numark-Mixtrack-Platinum-FX-scripts.original.js`](../../original/Numark-Mixtrack-Platinum-FX-scripts.original.js) — the JavaScript logic layer: numeric constants, value decoding (jog wheel, encoders), and every raw `midi.sendShortMsg`/`midi.sendSysexMsg` call used for LED and screen feedback that is **not** expressed in the XML.

## MIDI conventions used throughout

### Status byte anatomy

The controller uses standard MIDI status bytes, where the **high nibble** is the message type and the **low nibble** is the MIDI channel (0-15):

| Status range  | Message type   | Channel meaning on this controller                                                                                                                                                                                            |
| ------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0x80`–`0x8F` | Note Off       | `0x80+n` = deck `n+1` (n = 0-3), or `0x84+n` = pad grid on deck `n+1`                                                                                                                                                         |
| `0x90`–`0x9F` | Note On        | `0x90+n` = deck `n+1` transport buttons; `0x94+n` = pad grid / loop buttons on deck `n+1`; `0x98`/`0x99` = FX unit 1/2 select buttons & tap; `0x9F` = Load buttons (all decks share this one status, disambiguated by midino) |
| `0xB0`–`0xBF` | Control Change | `0xB0+n` = deck `n+1` pots/jog-turn/VU/spinner; `0xBE` = master gain; `0xBF` = global (crossfader, browse knob, headphone gains)                                                                                              |

So a deck index (0-3, for decks 1-4) is very often just added to a base status byte. **Two exceptions to watch for**: the pad grid / pad-mode / loop / setBeatgrid controls live on status `0x94-0x97`/`0x84-0x87` (i.e. base `+4` from the plain transport status `0x90-0x93`/`0x80-0x83`), and the crossfader/browse/headphone controls live on the shared `0xBF` channel rather than a per-deck one.

### How "Shift" is encoded

There is a physical **Shift** button (see [`decks-transport.md`](decks-transport.md#shift-button)), but it does **not** change the status byte of other controls the way a real MIDI "channel switch" would. Three different encoding patterns are used on the wire, and it's important to know which applies to a given control:

- **Pattern A — separate `<control>` block, same status, different midino.** Most transport buttons (Play, Cue, Sync, pitch-bend up/down, loop in/out/½/×2) send a _different_ midino when Shift is held, on the _same_ status byte. Example: Sync press is `0x90-93 / 0x02` unshifted, `0x90-93 / 0x03` shifted.
- **Pattern B — same status AND same status range, shift = `midino + 8` or a distinct constant.** The pad grid always uses status `0x94-97` (press) / `0x84-87` (release); Shift only changes the midino by `+8` (pad 1 unshifted = `0x14`, pad 1 shifted = `0x1C`). Two of the four pad-mode buttons (Hotcue, Sample) similarly have a genuinely distinct wire midino for their shifted bank; the other two (Autoloop, Fader Cuts) have **no separate wire code at all** — Mixxx detects Shift purely from software state when the same midino arrives. See [`pads.md`](pads.md) for the full breakdown, including one place where the XML's own comment is misleading.
- **Pattern C — the Shift button itself.** A single logical control (`shiftToggle`) is mapped **8 times** (press + release × 4 channels `0x90-93`/`0x80-83`), all sharing `midino 0x20`. This means the physical Shift button broadcasts on all four per-deck channels simultaneously; the script also uses _which_ status byte reported the press (`0x91`/`0x93`) to know a "right-side" Shift was used (relevant for the browse-knob button's preview-vs-load behavior).

### `<options>` meaning

- `<script-binding/>` — the value is routed to a JavaScript function in the mapping script rather than directly to a Mixxx control.
- `<normal/>` / `<invert/>` — used only for the crossfader: the value is passed straight to the `crossfader` Mixxx control, or inverted first. Two `<control>` entries exist for the crossfader (one `normal` on `0xBF`, one `invert` on `0xB1`) because of the 2nd-deck "fader cuts" pad mode, which rapidly re-sends crossfader position on a different channel than the physical crossfader — see [`mixer.md`](mixer.md#crossfader).

### Inputs vs. outputs

The XML preset declares almost all **inputs** as `<control>` entries, but only **one** kind of **output**: the Keylock LED (8 `<output>` entries). Every other piece of feedback to the controller — pad LEDs, mode-select LEDs, FX LEDs, the VU meter, the platter spinner/position bar, the BPM up/down arrows, and the entire numeric screen (BPM/rate/time/duration) — is driven by raw `midi.sendShortMsg`/`midi.sendSysexMsg` calls inside the JS, with no XML `<output>` declaration at all. All of that is catalogued in [`outputs.md`](outputs.md).
